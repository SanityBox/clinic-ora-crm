# אינטגרציה: סוכן CloudChat ↔ n8n ↔ CRM

```
CloudChat (AI Function) ──POST + x-roey-key──▶ n8n webhook ──▶ Code: נרמול ובדיקת קלט
                                                      │
                                                      ▼
                         Supabase RPC (x-agent-key, מפתח מכספת n8n) ──▶ תשובה בעברית לסוכן
```

- workflow ב-n8n: `Roey - קליניקת אורה · סוכן ↔ CRM` (קובץ: [n8n-workflow.json](n8n-workflow.json), בלי סודות: רק מזהי credentials).
- שני מסלולים:
  - `POST /webhook/roey-ora-create-ticket` עם `{name, phone, description, request_type}` → `agent_create_ticket`: מאתר לקוחה לפי טלפון או יוצר חדשה (מקור "סוכן AI"), ופותח קריאה בסטטוס "חדשה".
  - `POST /webhook/roey-ora-next-appointment` עם `{phone}` → `agent_next_appointment`: התור הקרוב בסטטוס "עתידי" (BR-08). זו שליפה, אבל ב-POST: הטלפון עובר בגוף הבקשה ולא בכתובת, כך שהוא לא נשמר בלוגים של כתובות.
- אבטחה בשתי שכבות: header auth על ה-webhook, ובבסיס הנתונים בדיקת sha256 של `x-agent-key` מול `private.integration_keys`. בלי מפתח, הפונקציה זורקת `unauthorized`.
- בקובץ הייצוא `n8n-workflow.json` המפתח הציבורי של Supabase מופיע כ-`<SUPABASE_PUBLISHABLE_KEY>`. כשמייבאים, מחליפים אותו במפתח של הפרויקט. המפתחות הסודיים נמצאים רק בכספת ה-credentials של n8n, ולא נכנסים לייצוא.
- הסוכן מקבל `ok:true` ומספר קריאה רק אחרי שהשמירה הצליחה. בכל כשל (קלט חסר, CRM לא זמין) חוזר `ok:false` עם הודעה, והסוכן לא מבטיח שנשמר.

## תכנון: שש השאלות (שלב 29)

| שאלה | תשובה |
|---|---|
| 1. מה מפעיל את התהליך? | Webhook בייצור (`roey-ora-create-ticket` או `roey-ora-next-appointment`), עם Header Auth (`x-roey-key`). הקורא: AI Function בסוכן, רק כשהלקוחה סיימה למסור את הפרטים. |
| 2. מה מסננים בכניסה? | Code מנרמל טלפון (972, רווחים, מקפים) ובודק קלט: שם, טלפון תקין ותיאור. קלט חסר מחזיר `invalid_input` מיד, בלי לפנות ל-CRM. |
| 3. לאן מתפצל? | קלט תקין ← CRM. קלט לא תקין ← תשובה לסוכן. תשובת CRM ← הצלחה או כשל, ובכשל או בבקשת נציגה גם העברה לנציגה. |
| 4. מה הפעולה? | קריאת RPC ל-Supabase: `agent_create_ticket` או `agent_next_appointment`, עם `x-agent-key` מהכספת של n8n. |
| 5. מה בלולאה? | אין לולאה. כל קריאה מטפלת בלקוחה אחת ובבקשה אחת. |
| 6. מה קורה בכישלון? | 5xx, 429 או timeout: ניסיון חוזר אחד אחרי שנייה. 401/403: בלי ניסיון חוזר. אחרי כשל: `ok:false` לסוכן (שלא מאשר), העברה לנציגה ב-CloudChat, ותקלה בבאנר ב-CRM. נפילה לא צפויה: Error Workflow. |

### למה כך
- **n8n ולא חיבור ישיר מהסוכן ל-Supabase:** ניטור. כל ריצה נשמרת ב-Executions, ורואים בדיוק מה נכנס ומה חזר לסוכן. אפשר להוסיף ניסיון חוזר, העברה לנציגה והתראה בלי לגעת בסוכן, והמפתח הסודי של ה-CRM נשאר בכספת של n8n ולא בהגדרות הסוכן.
- **POST גם לשליפה:** הטלפון עובר בגוף הבקשה ולא בכתובת, כדי שלא יישמר בלוגים של כתובות.
- **תמיד 200 עם `ok`:** ה-External Request של CloudChat שומר את גוף התשובה בשדה, והסוכן מחליט לפיו. קוד שגיאה לא היה מגיע לסוכן כטקסט שהוא יכול לפעול לפיו. לכן כל תשובה כוללת `ok` והודעה בעברית, וכשל אמיתי לא נבלע: הוא מעביר לנציגה ונרשם כתקלה.
- **timeout של 8 שניות לקריאה ל-Supabase (שלב 29, היה 15):** גם במקרה הגרוע (8 שניות, המתנה של שנייה ועוד 8) הסוכן מקבל תשובה תוך כ-20 שניות, הרבה לפני מגבלת ההמתנה של CloudChat.

### ייבוא לשרת n8n אחר
1. לייבא בסדר: [שגיאות](n8n-workflow-errors.json) ← [העברה לנציגה](n8n-workflow-handoff.json) ← [ראשי](n8n-workflow.json).
2. בתהליך הראשי, לעדכן את מזהי התהליכים (העברה לנציגה ו-errorWorkflow) למזהים החדשים.
3. תהליך מיובא מגיע כבוי ובלי credentials: לחבר את ה-credentials (מפתח ה-webhook, מפתח ה-CRM, מפתח CloudChat), להחליף את `<SUPABASE_PUBLISHABLE_KEY>`, ולפרסם את שלושתם. תהליך השגיאות רץ רק אם הוא מפורסם.
4. הגדרות שלושת התהליכים: אזור זמן `Asia/Jerusalem`, תגית "קליניקת אורה".

### העברה לנציגה והתראה על כשל בתוך CloudChat (10.10.2026, [תוכנית](../plans/2026-10-10-cloudchat-handoff.md))

אחרי התשובה מה-CRM, n8n מחליט אם אדם צריך להיכנס לשיחה. אם כן, דרך ה-API של CloudChat (credential בכספת, מוגבל לדומיין של CloudChat): מאתרים את השיחה לפי השדה `ora_phone`, מעבירים אותה לסטטוס "פתוחה" ב"איזור הצ'אטים" ומוסיפים תגית. כשל בקריאות האלה לא חוסם את התשובה לסוכן.

| בדיקה | תוצאה |
|---|---|
| בקשת נציגה (קריאה 1037) | השיחה עברה ל-`open` ונוספה התגית **"ביקשו נציגה"** ✓ (n8n 787) |
| כשל מבוים: מפתח ה-CRM הושבת לכמה שניות | הסוכן קיבל `ok:false` ולא אישר פנייה. השיחה עברה ל-`open` עם התגית **"CRM נכשל - לטפל ידנית"** ✓ (n8n 792). המפתח הופעל מחדש. |
| טלפון של הקליניקה (שגיאת קלט) | בלי העברה, הסוכן מבקש טלפון אחר ✓ (n8n 786) |

**התראה אקטיבית לנציגה (שלב 23, [תוכנית](../plans/2026-10-10-staff-alert-assign.md)).** שיחה פתוחה עדיין מחכה שמישהי תיכנס ותראה אותה. לכן אחרי התגית n8n גם **משייך את השיחה לנציגה התורנית** (`assign-agent`, הקבוע `ON_DUTY_AGENT_ID`. מאז שלב 26 הוא נמצא בתהליך המשותף "העברה לנציגה"). ב-CloudChat השיחה מופיעה אצל הנציגה ברשימת "שלי" באיזור הצ'אטים, עם התגית. **ההתראה הקופצת של CloudChat לא אומתה:** ההגדרה "שיחה שהוקצתה לי" סומנה והדפדפן אישר התראות, ובכל זאת בשלוש בדיקות (10.10, 16:17–16:33) לא הופיעה התראה. לכן ההתראה שאומתה היא הבאנר האדום במסך הראשי של ה-CRM, והשיוך ב-CloudChat הוא תור עבודה. ההתראה נשארת בתוך כלי המבחן, בלי טלגרם ובלי מייל.

### אף כשל לא נשאר שקט (שלב 26, [תוכנית](../plans/2026-10-10-error-alerts.md))

יש שלושה workflows, וכולם ב-repo בלי סודות:

| קובץ | תפקיד |
|---|---|
| [`n8n-workflow.json`](n8n-workflow.json) | הראשי: שני המסלולים (פתיחת פנייה, התור הבא). בבקשת נציגה, או כשה-CRM לא זמין **בכל אחד מהמסלולים**, הוא קורא לתהליך ההעברה. |
| [`n8n-workflow-handoff.json`](n8n-workflow-handoff.json) | **העברה לנציגה**, תהליך משותף: איתור השיחה ← פתיחה ← תגית ← שיוך לנציגה התורנית. אם אחד הצעדים נכשל, או שלא נמצאה שיחה עם הטלפון, הוא מדווח תקלה ל-CRM. |
| [`n8n-workflow-errors.json`](n8n-workflow-errors.json) | **שגיאות**: Error Trigger ← מדווח ל-CRM את שם התהליך, הצומת שנפל, ההודעה ומספר ההרצה. מוגדר כ-`errorWorkflow` של שני התהליכים האחרים. |

שני ערוצי ההתראה מכסים זה את זה. כשה-CRM נפל, ההתראה עוברת ב-CloudChat (שיחה משויכת לנציגה). כש-workflow ב-n8n נכשל או ש-CloudChat לא זמין, ההתראה נרשמת ב-CRM (`agent_report_incident`, מוגן ב-`x-agent-key`). היא מוצגת כבאנר אדום "תקלה בחיבור לסוכן" במסך הראשי, ונשארת שם עד שמישהי לוחצת "טופל" (שלב 28). מה שלא מכוסה: אם שרת n8n עצמו לא זמין, אף ערוץ לא מתריע. במקרה כזה הסוכן אומר ללקוחה שלא הצליח לרשום את הפנייה, ונותן וואטסאפ וטלפון.

| בדיקה | תוצאה |
|---|---|
| A · בקשת נציגה (קריאה 1046) | עברה בתהליך המשותף. השיחה האחרונה עם הטלפון נפתחה, קיבלה תגית ושויכה ✓ (n8n 819 ← 820) |
| B · כשל מבוים במסלול התור הבא (מפתח ה-CRM הושבת לכמה שניות) | הסוכן קיבל "לא ניתן לבדוק כרגע". השיחה האחרונה עם 052-555-0101 שויכה לנציגה, עם התגית "CRM נכשל - לטפל ידנית" ✓ (n8n 823 ← 824). המפתח הופעל מחדש. |
| C · בקשת נציגה עם טלפון שאין לו שיחה ב-CloudChat (קריאה 1047) | נרשמה תקלה ב-CRM: "ההעברה לנציגה נכשלה... צריך לחזור ללקוחה ידנית" ✓ (תקלה 1) |
| D · תהליך בדיקה זמני שזורק שגיאה | תהליך השגיאות רץ (n8n 826 ← 827), ונרשמה תקלה עם שם התהליך והצומת ✓ (תקלה 2). תהליך הבדיקה נמחק. |
| הבאנר במסך הראשי | מופיע במחשב ובנייד (375px), בלי גלילה אופקית ובלי הפרות נגישות (axe) ✓ |

**ניסיון חוזר לפי סוג השגיאה (שלב 28, לפי טבלת הקודים בקורס):** בשני צמתי ה-Supabase אין `retryOnFail`. בענף השגיאה, הצומת "שגיאה זמנית?" מסווג את הקוד. ב-5xx, 429 או בלי תשובה (timeout) יש המתנה של שנייה וניסיון שני אחד. ב-401/403 אין ניסיון חוזר: עוברים ישר לכשל, להעברה לנציגה ולתשובה לסוכן. נבדק: מפתח CRM מושבת ← 401, ניסיון אחד בלבד, והשיחה הועברה (n8n 841). ענף ה-5xx נבדק על הסיווג בלבד (500, 503, timeout ו-429 ← ניסיון חוזר. 401 ו-403 ← בלי), כי אי אפשר לביים 5xx מול השרת החי.

**מוקש:** ב-n8n 2.x תהליך השגיאות רץ רק אם הוא **מפורסם** (Publish). בניסיון הראשון הוא לא היה מפורסם, ושום דבר לא קרה.
